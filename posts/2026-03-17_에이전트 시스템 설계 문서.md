## 1. 브리핑 문서란

​

프론티어 모델 과 에이전트는 모두 컨텍스트가 초기화된다. 브리핑 문서는 이 초기화를 넘어 프로젝트 맥락을 보존하는 유일한 수단이다. 브리핑 문서는 과거와 현재, 미래에 사용자가 작업하고 있는 내용을 확인, 점검 할 수 있는 도구다.

​

| 특성 | 내용 |

| ----- | ----------------------------------------------------------------------------------------------------------- |

| 위치 | `X/Y/{프로젝트명}/{파일명}.md` — 폴더명은 에이전트 작업 규범 파일명/폴더 규칙을 따른다 (프로젝트명과 파일명은 네이밍 에이전트가 5회 시도하여 나온 값을 연산 모델을 통해 결정하도록 한다) |

| 내용 결정 | (관리자) 에이전트 |

| 파일 작성 | (실무자) 에이전트 |

| 갱신 시점 | 체크박스 항목 완료 시 + 세션 종료 시 |

| 독자 | 다음 세션의 (담당자) 에이전트 |

​

> [!warning] 브리핑 없이 프로젝트 작업 시작 금지

> 세션 시작 시 브리핑을 먼저 확인하지 않으면 이미 결정된 사항을 재논의하거나 완료된 작업을 반복하는 낭비가 발생한다.

## 2. 브리핑 문서 구조

​

브리핑 문서의 필수 섹션은 아래 6 개다. 나머지 구조(순서, 추가 섹션 등)는 (담당자) 에이전트가 자율적으로 결정한다. 기본대원칙 설계 안에서 실무를 맡는 (담당자) 에이전트의 판단을 최우선한다. 프로젝트 브리핑 작성 전, (사용자)의 의도를 정확히 확인하고, 만약 보완할 내용이 있다면 규범에 추가하여, 개선한다. 프로젝트가 유연하게 운영될 수 있는 만큼, (임원) 에이전트와 (관리자) 에이전트의 개입 점수는 점진적으로 모델에 맞게 조율한다.

​

### 프로젝트 목표

​

이 프로젝트가 달성하려는 것. 변경되지 않는 한 고정.

​

### 완료 기준

​

프로젝트가 끝났다고 판단하는 조건. 체크박스(`- [ ]`) 형식.

모든 항목이 `- [x]` 가 되면 프로젝트 완료.

​

### 현재 단계

​

지금 전체 흐름 중 어느 지점에 있는지 한 줄로.

예: `기능 구현 완료 → 문서화 단계`

​

### 결정 로그

​

결정된 사항과 그 이유를 표로 기록. 비효율적 재논의 방지가 목적.

​

| 결정 | 이유 |

|---|---|

| 결정 내용 | 왜 이렇게 했는지 |

​

- 시간순 누적. 삭제 금지.

- `- [x]` 처리된 항목 중 "왜 그렇게 했는지 이유를 기록할 가치가 있는 것"은 이 표로 이동. 판단은 (관리자) 에이전트 가 한다.

​

### 다음 할 일

​

체크박스(`- [ ]`) 형식으로 우선순위 순 나열. 최상단이 다음 세션 시작점.

항목 완료 시 `- [x]` 로 변경 후 브리핑 갱신. `- [x]` 항목은 그대로 유지한다.

​

### 보류/이슈

​

막힌 것, 미결 사항, (사용자) 결정이 필요한 항목. 해당 없으면 생략.

## 3. 작성 시점

​

아래 경우에 브리핑 문서를 신규, 정정 작성한다. 작성은 (담당자) 에이전트의 전적인 권한임을 존중한다.

​

1. \*\*새 프로젝트 시작 시\*\* — 목표가 정해지고 2 회 이상 세션이 예상될 때

2. \*\*기존 프로젝트에 브리핑이 없을 때\*\* — 첫 세션 종료 처리 전 소급 작성

3. \*\*프로젝트 변경 시\*\* — 프로젝트가 진행되면서 원래 내용과 바뀌었을 때

​

---

​

## 4. 브리핑 작성 전 필수 질문

​

브리핑 작성 전 (담당자) 는 (사용자) 에게 자율적으로 임의의 3가지를 반드시 질문한다. 답변을 받은 후 브리핑 작성을 시작한다. 반드시 억지로라도 3개 이상 질문하도록 한다. (담당자) 에이전트가 질문을 누락하는 경우, 페널티를 처리하고, 누적된 에이전트는 해당 업무에서 배제한다.

## 5. 업데이트 규칙

​

| 항목 | 규칙 |

| ------ | ----------------------------------- |

| 갱신 시점 | 체크박스 항목 완료 시 · 세션 종료 시 |

| 현재 단계 | 작업 흐름이 바뀌면 즉시 반영, 또는 사용자에게 제안 |

| 완료 섹션 | 추가만. 삭제 금지 |

| 다음 할 일 | 완료 항목은 `- [x]` 표시만 유지 · 우선순위 재정렬 포함 |

## 6. 세션 시작 절차

​

1. 메모리에서 해당 프로젝트 브리핑 경로 확인

2. 경로가 없으면 (사용자) 에게 요청

3. 에이전트에 브리핑 읽기를 위임 후 요약 보고받기

4. 현재 단계·다음 할 일 파악 후 (사용자) 방향과 정렬해 작업 시작

​

> [!tip] 사용자가 먼저 방향을 제시해도 브리핑 먼저

> 세션 시작 시 사용자가 이미 할 일을 지시했더라도, 브리핑을 확인해 맥락을 정렬한 뒤 시작한다.

> 사용자도 실수를 할 수 있다.

​

## 7. 에이전트 지시 시 필수 포함 요소

​

브리핑 문서 작성을 에이전트에 위임할 때, 지시 프롬프트에 아래 3 가지를 반드시 포함한다.

​

| 요소 | 설명 |

|---|---|

| 저장 경로 | 파일을 만들 볼트 내 상대 경로 |

| 프로젝트 이름·목적·맥락 | 에이전트가 파일명·내용을 판단하는 기준 |

| 필수 섹션 내용 | (임원) 에이전트가 직접 구성해서 전달. 나머지 구조(순서·추가 섹션)는 타 에이전트 자율, Lv3 이상 에이전트의 승인이 있었다면 Ok. 승인 에이전트 기록 반드시 남길 것 |

​

> [!tip] 에이전트가 구조를 결정한다

> (임원) 에이전트는 필수 섹션 내용만 전달한다. 에이전트가 [[01\_에이전트 문서 작성 규범]]을 읽고 전체 구조(순서, 추가 섹션 등)를 결정한다. (임원) 에이전트 는 문서 작성 구조나 규격이 궁금하면 에이전트를 통해 간략하게 물어볼 수 있다.

## 8. 세션 종료 절차

​

​

세션종료처리는 사용자가 "세션종료처리"라고 입력하면 실행되는 고정 커맨드다. 아래 순서로 진행한다.

​

1. \*\*현재 작업중이던 브리핑 업데이트\*\* — 결정 로그·다음 할 일·보류 갱신

2. \*\*결과 요약\*\* — 이번 세션에서 한 것 한 줄 요약

3. \*\*다음 세션 시작점 명시\*\* — 브리핑의 "다음 할 일" 최상단 항목

​

> [!info] 프로젝트 상태는 브리핑이 단일 진실 공급원

> (에이전트) 메모리에 프로젝트 상태를 중복 저장하지 않는다. 메모리는 피드백·도구 규칙 등 전역 정보만 저장.
